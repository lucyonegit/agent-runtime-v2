# Agent Runtime V2 修订版分阶段实施计划

> **更新说明**：本计划合并了对原始重构方案的深入评审反馈（特别是关于数据一致性、恢复幂等性、锁归属等 P0 级风险的修复），并全面采用了新的[命名优化方案](./04-命名优化方案.md)。

**目标:** 构建一个以 `agent_messages` 为事实来源、以 `Job` 为调度与恢复核心、基于事务强一致性和明确边界的 Agent Runtime 系统。

---

## 阶段 0：建立绿色基线与回归保护 (P0)

> **背景**：当前代码库缺少干净的基础，强行在红色的基线上重构会导致故障原因无法定位。

- [ ] **0-a.** Git 初始化，并将当前状态 commit，打下可回滚的 tag 基线。
- [ ] **0-b.** 修复现有 `src/orchestration/react-agent.ts` 及其相关文件中的 TypeScript 类型和语法错误，确保 `npm run typecheck` 跑通。
- [ ] **0-c.** 固定 PostgreSQL 测试环境（建议引入 Testcontainers 或基于 Docker Compose 的标准配置），确保不会因为默认 `127.0.0.1:5433` 连不上导致测试套件崩溃。
- [ ] **0-d.** 运行全部测试。对于因旧设计导致无法跑通的 case，用 `.todo` 或 `.fails` 标记跳过，**确保 `npm test` 呈绿色状态**。
- [ ] **0-e.** 盘点 `src/storage` 中的现有代码，整理出“已实现/未实现”矩阵，避免在后续阶段重复造（Schema 初始化、旧有查询）的轮子。

## 阶段 1：Schema 奠基与领域模型 (P0/P1)

- [ ] **1-a. 新命名表与列**：创建规范的 `schema.ts`，使用新命名（`agent_jobs`, `agent_messages`, `agent_plans`, `agent_summaries`, `agent_model_calls` 等），并显式声明各种外键和约束。
- [ ] **1-b. `message_type` 扩展**：将消息类型定义为开放字典，为异常记录、代码工作台结果等新类型制定扩展规范（需同步明确其 `visibility` 及所属的 `MessageGroup`）。
- [ ] **1-c. 引入 `invocation_status`**：为 `agent_messages` 中的 tool call 添加执行状态列（如 `pending`, `completed`, `orphaned`），这是后续安全恢复的基础。
- [ ] **1-d. 性能基线**：对 Context 投影查询、`StepOutput` 检索和 pending `UserInput` 锁定查询加上复合索引，并编写对应的 `EXPLAIN ANALYZE` 检查，确保查询不随行数增加退化。

## 阶段 2：AgentLoop 与 AgentRunner (P1)

> **背景**：核心执行循环必须放弃工具执行权，改为由外层协调持久化与副作用，防止因数据库宕机而产生不可追踪的脏数据。

- [ ] **2-a. `AgentLoop` 纯化**：将原有 Core 改造为单纯产生 `LoopEvent` 的 AsyncGenerator。**它只负责调 LLM，不负责执行工具**。
- [ ] **2-b. `AgentRunner` 驱动与持久化**：`AgentRunner` 接收到 tool calls 时，**必须先通过 `MessageWriter` 提交事务落库**。提交成功后，Runner 才执行工具，并将结果再喂回给 `AgentLoop`。
- [ ] **2-c. 严格串行写入 (P0)**：在 `MessageWriter` 或 `AgentRunner` 层实现单 session 的写入串行化锁，确保 `row_id`（bigserial）的分配顺序与数据库事务的提交顺序绝对一致，修复潜在的 cursor 漏读漏洞。
- [ ] **2-d. 工具幂等性契约 (P0)**：
  - 定义工具接口的 `sideEffectLevel`: `read_only` | `idempotent` | `side_effecting`。
  - 定义 `idempotency_key`（默认使用 `toolCallId`）。
  - 对于 `side_effecting` 工具，如果在落库前崩溃，重启后识别出 `invocation_status = orphaned`，必须转为进入 `unknown` 状态并产生 `UserInput` 让用户人工确认，绝不自动重放副作用。

---

## 阶段 3：JobScheduler 与事务命令集 (P0/P1)

- [ ] **3-a. Lock 归属分治 (P0)**：明确 `Job` (原 root task) 拥有整个工作流的排他性 lock。`StepRun` (原 child task) 只负责保存当前步骤的断点状态。恢复与调度权完全属于持有 `Job` 锁的 worker。
- [ ] **3-b. 明确 failed 终态 (P0)**：取消 `failed -> resuming` 的转换。`Job` 一旦失败即到达终态，若需重试，必须创建新的 `Job` (引用 `retry_of_task_id`)，避免触发部分唯一索引冲突。
- [ ] **3-c. 原子事务命令集**：实现并测试下列强一致性操作：
  - `createJobAndAppendMessage`
  - `commitToolCall` & `commitToolResult`
  - `createInputRequestsAndMarkWaiting`
  - `answerInputAndClaimResume` (加锁读取 Request -> 记录回答 -> 检查是否全部 Pending 结束 -> 尝试 Claim Lock -> 返回 true/false)

## 阶段 4：ContextBuilder 上下文管道 (P1)

- [ ] **4-a. 基于 `usage` 的投影**：统一所有上下文获取逻辑，根据 `conversation`, `step_execution` 等不同的 usage 从数据库拉取指定 scope 的数据。
- [ ] **4-b. `MessageGroup` 原子性保障**：在 context mapper 中确保 assistant 的 tool calls 与它们对应的 results 作为整体进行 token 预算，截断时同进同出。
- [ ] **4-c. `summary-store.ts` 压缩链**：实现按 `context_rules_version` 管理的压缩快照。Token 预算超标时触发生效，生成快照行存入 `agent_summaries`。
- [ ] **4-d. `agent_model_calls` 审计记录**：执行 LLM 之前创建记录，返回后写入真实 Token usage，异步汇总到 `agent_usage_stats`。

---

## 阶段 5：PlanEngine 与 StepRunner (P1)

- [ ] **5-a. `PlanEngine` 路由审计**：在 `PlanEngine` 进行直接回答 vs 创建计划的路由决策时，将对应 context build 的 `call_id` 记录到 `agent_jobs.route_decision_build_id` 中以便事后诊断。
- [ ] **5-b. 统一 `StepOutput` 校验**：`StepRunner` 在收到 `AgentLoop` 结束（completed）信号时，**负责在代码层做结构化校验**，而非要求大模型用特化工具自己 commit。
- [ ] **5-c. 强类型最终报告**：`StepOutput` 以严格 schema (`summary`, `artifacts`, `unresolved`) 存入。所有步骤完成后，`PlanSummarizer` 只加载最初的目标、最终 Plan 以及 `StepOutput` 数组，组装出纯净的 final context。

---

## 阶段 6：SessionView 与 SSE 通信 (P1)

- [ ] **6-a. `timeline.ts` 纯函数抽象**：提取统一的投影纯函数。支持扁平时间线 (flat) 和聚拢按步骤 (grouped) 视图。
- [ ] **6-b. MVP 版 SSE 重连协议**：
  - 断线重连时，客户端直接发起全量 `GET /view` 拉取最新状态，暂不实现复杂的事务发件箱（outbox）。
  - 所有 entity patch 附带 `version`，前端 Reducer 拦截旧版本覆盖新版本，处理并发更新时的乱序。
- [ ] **6-c. 更新前端模型映射**：将 Web 层的 Store、Action 均迁移到新名词空间（如 dispatch `JOB_UPDATED` 替代 `TASK_UPSERTED`）。

## 阶段 7：清理与非功能性验收 (P1/P2)

- [ ] **7-a. `FileSessionStore` 降级**：考虑到文件存储无法支持阶段 3 中的强事务操作，在 `session-store.ts` 接口上明确标记需事务支持的方法；针对 `FileSessionStore` 直接抛出 `NotSupportedError`，或完全将其移除。
- [ ] **7-b. 遗留逻辑剔除**：清理所有依靠旧版本 Metadata JSON 去解析树关系的兼容代码。
- [ ] **7-c. 非功能性验收测试**：
  - [ ] 验证单次 context build (P95 延迟) < 500ms
  - [ ] 100 条消息的 `GET /view` 延迟 < 200ms
  - [ ] 10 并发 session 下的 SSE 更新不丢失任何 `RealtimeEvent`
  - [ ] 脚本 `reset-agent-runtime-schema.ts` 运行到准备完毕耗时 < 3s
