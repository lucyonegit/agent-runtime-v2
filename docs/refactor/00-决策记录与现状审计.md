# Agent Runtime V2 重构决策记录与现状审计

> 本文是后续重构的边界条件。它把此前围绕会话、ReAct、Planner、HITL、流式、上下文压缩、Code Agent 和 UI 的讨论收敛成可执行的决策，避免再次从零开始争论术语。

## 1. 目标

构建一个以**持久化会话时间线**为事实来源的 Agent Runtime：

- 简单问题由 ReAct 直接回答。
- 复杂目标由同一个根任务进入规划、分步执行和汇总。
- 每个规划步骤内部仍由通用 ReAct 执行工具。
- 支持工具型 HITL、恢复、流式输出、上下文压缩、真实 token 用量、Code Agent 和 UI 投影。
- UI 实时消费与刷新恢复消费同一套持久化实体；唯一例外是未落库的 delta。

## 2. 已确定的核心决策

| 主题 | 决策 | 原因 |
| --- | --- | --- |
| 会话事实来源 | `agent_messages` 是唯一对话时间线 | 不维护一套“给 UI 的假消息”和一套“给模型的会话” |
| 顺序 | `agent_messages.row_id` 由 PostgreSQL `bigserial` 生成 | 全局单调、可做 cursor，不需要 session 内手工分配 `seq` |
| UI 数据 | UI 的完整状态来自持久化实体；SSE 只发送实体 upsert 与临时 delta | 刷新后 `GET /view` 与实时过程一致 |
| 工具调用 | `tool_call` 和 `tool_result` 分别持久化为消息行；ContextUnit 在构建模型上下文时把它们配对 | 满足 OpenAI/LangChain 协议，又保留可审计的时间线 |
| 工具批处理 | 同一轮多个普通工具先全部执行；HITL 工具只创建请求，不丢弃其他工具结果 | 恢复时不会丢失已经发生的副作用 |
| HITL | `request_user_input` 是标准工具；支持 `text`、`single_choice`、`multi_choice`、`approval` | 不是 UI 特例，也不需要 `ModelInputRequired` |
| HITL 回填 | `answer_as_tool_result` 默认用于工具型等待；`answer_as_user_input` 仅用于确实要作为新用户话语的场景 | 保持 tool call/result 成对，避免伪造对话 |
| 多个等待 | 同一任务可有多个 pending input request；全部回答后才 claim resume | 支持并行表单/审批，避免多标签页重复恢复 |
| 活跃任务 | 一个 session 同时只允许一个 active root task | 解决多窗口冲突；子任务属于 root task |
| 恢复 | `agent_tasks + agent_plans + agent_plan_steps + agent_input_requests + agent_messages` 就是 checkpoint | 不增加语义重叠的 `agent_runs` 或 checkpoint 表 |
| Planner | Planner 不是独立公开入口，也不能把整套 Planner 当成普通无状态工具函数 | 它是根任务内部的 workflow capability：路由、建计划、推进步骤、汇总 |
| 规划步骤 | 每个 `planner_step` 由通用 ReAct 执行，必须显式产出 `step_result` 才能完成 | 工具结果不等于步骤稳定结论 |
| 最终报告 | 只读取 plan + `step_result` | 不吞入失败搜索、模型自我修正和 raw tool output |
| 系统提示词 | 系统提示词是运行时输入记录，默认 `visibility=internal` | 需要审计，但不能被 UI 当对话内容展示 |
| 上下文 | 不把完整会话直接塞进每次模型调用；按 purpose 投影、预算、快照、尾部组装 | 防止上下文膨胀和跨 step 污染 |
| 压缩 | 快照有 scope、purpose、projection version，不再只有 session rolling summary | planner step、最终汇总、code project 的记忆边界不同 |
| Code Agent | Code Agent 使用独立会话模式和独立 UI 路由；代码文件只在 sandbox，运行数据在 PostgreSQL | 不把代码工作台混入通用 Agent UI |

## 2.1 讨论演进摘要

以下不是逐字聊天记录，而是按问题演进整理的可追溯结论：

1. **会话与 UI**：最初 runtime 将会话存储、context builder、UI event 混在一起。结论是 messages 必须作为事实时间线，UI 是投影，流式 delta 是唯一不持久化的临时数据。
2. **工具与协议**：讨论过 `final_answer` 工具、tool call/result 是否必须成对、HITL 的返回方式。结论是移除强制 final tool；tool call/result 独立行持久化并在模型 context 中配对；HITL 使用真实工具回填。
3. **状态与恢复**：讨论过 `agent_runs`、checkpoint、row lock、session seq。结论是 task 是 checkpoint，`row_id` 取代人工 seq，lease + version 防多窗口恢复冲突。
4. **Planner**：讨论过 Planner 独立 agent、Planner 作为普通工具、Planner + ReAct 组合。结论是 Planner 是 root task 内的 workflow capability；step 内由共享 ReAct 执行，不能把 Planner 变成无状态工具函数，也不对外暴露旧入口。
5. **上下文**：发现每个 step 写入 ReAct system prompt，context builder 又从 session 全量取消息。结论是按 purpose projection；step 使用 previous step result，而不是 previous step raw runtime。
6. **存储结构**：从 metadata 中读 `stepId`/`planId` 无法支持恢复和聚合。结论是关系字段入列、plan/step 入专表，metadata 退回扩展用途。
7. **UI**：讨论了平铺与按 step 聚合。结论是 API 保留 flat canonical timeline，同时返回 derived grouped timeline；用户可在前端切换视图。
8. **Code Agent**：代码工作区与 artifact/download/tmp 的物理文件留在 sandbox；项目、任务、消息、上下文、用量数据留在 PostgreSQL；Code UI 与通用 Agent UI 路由分开。

## 3. 已否决或不采用的方案

| 方案 | 结论 | 问题 |
| --- | --- | --- |
| `agent_runs` 作为每轮执行表 | 不采用 | 与 task checkpoint、context build 和 message timeline 重复，恢复语义不清 |
| `ModelInputRequired` 事件/工具 | 不采用 | 普通追问是正常 assistant final；只有显式 HITL 工具才进入等待状态 |
| 以 `toolCalls.length === 0` 判定任务完成 | 不采用 | 无工具不等于完成；空模型输出、迭代耗尽和普通回答必须区分 |
| 强制 `final_answer` 工具 | 不采用 | 把普通自然语言回答伪装成工具调用，损失一次正常 ReAct 回合 |
| session 内人工 `seq` | 不采用 | 需要并发分配和锁；数据库 `row_id` 已提供稳定 cursor |
| 仅用 metadata 保存 `planId`/`stepId`/`projectId` | 不采用 | 关键关系无法建立约束和索引，context/view 必须 JSON 解析 |
| 单一 session rolling summary | 不采用 | step、最终报告、code project 会互相污染 |
| UI timeline 只在前端自己猜测聚合 | 不采用 | 同一逻辑会在 SSE、GET view、前端重复三份并漂移 |
| Planner 的每个 step 继承所有旧 ReAct prompt 和 raw messages | 不采用 | context 膨胀、缓存失效、错误过程进入最终答案 |

## 4. 当前实现的问题审计

### 4.1 Core 层

`src/core/react/react-core.ts` 仍是值得保留的通用循环，但当前实现有四个需要优先修复的行为问题：

1. 先执行工具，后才产生 assistant tool-call completed event。外部副作用可能先发生、消息尚未入库。
2. 空输出和达到最大迭代次数会静默退出；上层可能误标 `completed`。
3. 单个工具抛错会中断同轮其他工具，不能沉淀为 `tool_result(status=failed)`。
4. 流式 tool args 解析失败时会被静默忽略，导致模型协议与会话历史不一致。

Core 不应该知道 PostgreSQL、SSE、plan 或 UI；它只需要返回可判定的 step outcome，并保证事件顺序正确。

### 4.2 编排层

`src/orchestration/react-agent.ts` 与 `src/orchestration/planner-react-agent.ts` 都在做：创建 task、追加 message、处理 core event、创建 HITL、更新状态、记录 token、发送 patch。重复逻辑导致：

- direct、planner step、code 的消息 metadata 和 patch 形状逐渐不一致；
- HITL answer 的持久化顺序容易不满足外键和 tool pair；
- `planner-react-agent.ts` 同时承担路由、计划、step 执行、最终汇总、持久化和 SSE，难以测试与恢复；
- step 关系靠 `metadata.stepId` 识别，无法可靠索引。

### 4.3 Context 层

`src/context/context-builder.ts` 虽然接收 `taskId`，但会读取 session 的全部 messages。`planner-context-projection.ts` 又单独拼了一份 step context。结果是两个 context builder 并存，且都可能把不应进入本次调用的消息带入。

### 4.4 Storage 与 View

旧初始化函数同时做 DDL、`ALTER TABLE`、旧模式迁移、`seq` 回填、metadata 推断。这不适合启动路径。View 聚合在服务端和前端各有一份，导致 timeline 展开/按 step 聚合难以保持一致。

## 5. 方案比较

### 方案 A：只拆文件，保留现有调用方向

优点：改动短、风险表面小。

缺点：核心事件持久化顺序、恢复原子性、context 投影和 UI 重复逻辑都仍然存在。它只是把复杂度移动到更多文件，不是重构。

### 方案 B：保留 ReAct Core，重建运行时边界（推荐）

优点：

- ReAct 保持通用，Planner/Code 都能复用；
- 持久化顺序、lease、HITL 恢复被收口到 `TaskRuntime` 和 `CoreEventRecorder`；
- `PlannerWorkflow` 只关心 plan 生命周期，`PlannerStepExecutor` 只关心单 step；
- ContextPipeline 能按 purpose 复用，不再让每个 agent 自己拼 messages；
- 可以分阶段替换，不需要一次推翻 UI。

缺点：需要先定义 domain/store 关系，并补齐更多集成测试。

### 方案 C：引入 LangGraph 或完整图执行引擎

优点：天然有节点 checkpoint 和图恢复模型。

缺点：当前代码已具备可控的 task/message 持久化基础；立即迁移会同时改变模型调用、工具、状态和存储，调试成本大，且不能自动解决 UI/上下文边界。当前不采用。

## 6. 最终推荐

采用方案 B：**保留并修正 ReactCore；将编排拆成 workflow、task runtime、event recorder、context pipeline 和 shared view projection；PostgreSQL 使用一份干净的 canonical schema；用阶段迁移替代启动期兼容脚本。**
